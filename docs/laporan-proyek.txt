BAB I  
PENDAHULUAN

1.1 Latar Belakang

Bidang Aplikasi Informatika (APTIKA) pada Dinas Komunikasi, Informatika, dan Statistik (Diskominfotik) Provinsi Riau memegang peranan krusial dalam menyelenggarakan tata kelola dan implementasi Sistem Pemerintahan Berbasis Elektronik (SPBE). Tingginya intensitas agenda kedinasan—seperti rapat koordinasi antarperangkat daerah, bimbingan teknis, sosialisasi aplikasi, dan evaluasi layanan TI—menuntut pengelolaan jadwal dan dokumentasi administrasi yang tertib dan akuntabel. Namun, observasi di lapangan menunjukkan koordinasi jadwal serta distribusi berkas arsip resmi (surat tugas, notulen rapat, dan dokumentasi foto) masih dilakukan secara informal melalui pesan instan WhatsApp. Pola ini mengakibatkan informasi agenda rawan tertimbun percakapan lain, proses temu kembali berkas fisik untuk audit kinerja memerlukan waktu lama, serta belum adanya portal pantau mandiri bagi pegawai non-admin.

Guna mengatasi kendala tersebut, dirancang sistem informasi administrasi kegiatan berarsitektur Hybrid Desktop. Sistem memanfaatkan ketangguhan logika framework Laravel yang dikemas menggunakan desktop wrapper Electron, serta terintegrasi langsung dengan cloud database Supabase PostgreSQL dan cloud storage Supabase Storage S3. Pendekatan ini memungkinkan aplikasi dieksekusi secara mandiri (self-contained) pada komputer kerja pengguna tanpa memerlukan instalasi server web tambahan maupun alokasi anggaran sewa hosting publik bulanan.

Berdasarkan urgensi tersebut, disusun laporan Kerja Praktik berjudul “SISTEM INFORMASI ADMINISTRASI KEGIATAN BIDANG APTIKA BERBASIS APLIKASI DESKTOP”. Proyek ini menghasilkan dua produk aplikasi desktop Windows, yaitu SIAPTIKA Administrator (.exe) untuk pengelolaan penuh agenda dan arsip kedinasan terautentikasi, serta SIAPTIKA Dashboard (.exe) sebagai portal informasi agenda kegiatan terbuka (read-only) bagi seluruh aparatur di lingkungan Bidang APTIKA Diskominfotik Provinsi Riau.

Tujuan dari pelaksanaan Kerja Praktik dan pengembangan sistem ini adalah:

2. Merancang sistem informasi administrasi kegiatan berarsitektur hybrid desktop yang memadukan keunggulan logika web Laravel dengan antarmuka desktop Electron.
3. Membangun aplikasi desktop mandiri SIAPTIKA Administrator (.exe) dan SIAPTIKA Dashboard (.exe) yang terintegrasi aman dengan basis data dan penyimpanan cloud Supabase.
4. Menguji kelayakan fungsional sistem menggunakan metode Black Box Testing guna memastikan keandalan seluruh fitur sesuai spesifikasi kebutuhan dinas.

BAB III  
PELAKSANAAN DAN PEMBAHASAN KERJA PRAKTEK

3.1 Landasan Teori dan Teknologi

3.1.1 Konsep Sistem Informasi Administrasi dan Arsip Digital

Sistem informasi administrasi merupakan susunan terpadu perangkat keras, perangkat lunak, data, prosedur, dan sumber daya manusia yang mengelola dan mendistribusikan data guna mendukung koordinasi operasional serta akuntabilitas agenda kedinasan sektor publik (O'Brien & Marakas, 2017; Laudon & Laudon, 2020). Dalam tata kelola kearsipan digital, sistem wajib mengelola siklus hidup dokumen elektronik mulai dari penciptaan, pengorganisasian aman, hingga penemuan kembali (retrieval) (Read & Ginn, 2015). Mengacu pada standar ISO 15489-1 (2016), sistem kearsipan andal wajib menjamin aspek keaslian (authenticity), keandalan (reliability), integritas (integrity), dan kemudahan akses (usability) guna mengeliminasi risiko kerusakan fisik naskah dinas saat audit kinerja (Sutirman, 2019). Pada SIAPTIKA, konsep ini diwujudkan dengan menghubungkan pencatatan agenda kedinasan dengan repositori berkas resmi (surat tugas, notulen rapat, dan foto kegiatan) secara relasional dalam satu kesatuan sistem.


3.1.2 Arsitektur Aplikasi Desktop Hybrid

Arsitektur desktop hybrid memadukan teknologi web (HTML, CSS, JavaScript, dan PHP) pada lapisan logika bisnis dengan lingkungan eksekusi desktop native melalui embedded browser engine (Ferreira et al., 2018; Griffiths, 2019). Pada SIAPTIKA, web service internal Laravel dijalankan pada loopback lokal (127.0.0.1) dan dimuat oleh jendela Electron mandiri tanpa peramban eksternal, menghasilkan aplikasi Windows (.exe) siap pakai tanpa instalasi server terpisah sekaligus meniadakan biaya sewa server hosting publik bulanan. 3.1.3 Framework Laravel dan Eloquent ORM

Laravel merupakan kerangka kerja PHP berbasis arsitektur Model-View-Controller (MVC) yang memisahkan logika manipulasi data (Model), penyajian antarmuka (View via Blade), dan pengendalian lalu lintas permintaan (Controller) (Stauffer, 2019; Pressman & Maxim, 2020; Sommerville, 2016). Manipulasi data dikelola oleh Eloquent ORM berbasis pola ActiveRecord (Fowler, 2018) yang memetakan tabel basis data ke dalam kelas model PHP secara berorientasi objek tanpa penulisan sintaks SQL mentah, sementara Database Migration menjamin konsistensi skema tabel antar-lingkungan pengembangan. 3.1.4 Electron Framework dan Bundled Portable PHP Runtime

Electron menggabungkan mesin render Chromium dan runtime Node.js untuk mengeksekusi aplikasi desktop berbasis teknologi web melalui Main Process (pengendali siklus hidup dan akses sistem operasi) dan Renderer Process (penampil antarmuka grafis) (Griffiths, 2019). Pada SIAPTIKA, Main Process mengeksekusi child process spawning untuk mengaktifkan web server PHP lokal portabel (PHP 8.3 Thread-Safe) saat aplikasi dibuka dan menghentikannya secara bersih (graceful termination) saat jendela ditutup. Penerapan single-instance lock mencegah konflik alokasi port jaringan lokal, sehingga staf dapat menjalankan aplikasi tanpa perlu menginstal web server (Laragon/XAMPP), Composer, maupun Node.js secara manual.


3.1.5 Basis Data Cloud Supabase PostgreSQL dan Supabase Storage (S3 Protocol)

Supabase merupakan platform Backend-as-a-Service berbasis basis data relasional PostgreSQL yang menjamin integritas referensial data dan kepatuhan transaksi ACID—Atomicity, Consistency, Isolation, dan Durability (Silberschatz et al., 2020). Pertukaran data antara aplikasi desktop klien dan database cloud diamankan melalui protokol koneksi terenkripsi SSL/TLS. Selain basis data relasional, Supabase Storage berbasis protokol AWS S3 digunakan sebagai repositori privat terpusat untuk menyimpan berkas dokumen arsip kedinasan (PDF dan gambar), sehingga berkas terlindung dari risiko kerusakan lokal dan dapat diakses secara simultan oleh staf dinas.


3.1.6 Metodologi Pengembangan Perangkat Lunak Scrum

Scrum merupakan kerangka kerja pengembangan perangkat lunak berbasis nilai Agile yang berfokus pada kolaborasi, adaptabilitas, serta penghantaran produk secara bertahap dan berulang melalui siklus Sprint berdurasi tetap (Schwaber & Sutherland, 2020; Pressman & Maxim, 2020). Pada proyek SIAPTIKA, metodologi Scrum diterapkan ke dalam 6 (enam) tahapan sprint mencakup Product Backlog, Sprint Planning, Daily Coordination, Sprint Review, dan Sprint Retrospective, yang memungkinkan penyelarasan kebutuhan antarmuka, validasi aturan bisnis arsip, dan pengemasan biner desktop terlaksana secara terukur.

b. Kebutuhan Non-Fungsional (Non-Functional Requirements)
Kebutuhan non-fungsional menetapkan kriteria kualitas operasional dan performa sistem SIAPTIKA:
1. Aspek Kinerja (Performance): Waktu inisialisasi aplikasi desktop (startup time) hingga siap digunakan tidak melebihi 3 detik, serta waktu eksekusi kueri penelusuran data berada di bawah 1 detik pada jaringan standar.
2. Aspek Keamanan (Security): Kata sandi Administrator diamankan dengan enkripsi hash Bcrypt satu arah, rute administratif diproteksi middleware autentikasi sesi, dan pertukaran data ke Supabase dienkripsi melalui protokol SSL/TLS dan HTTPS.
3. Aspek Portabilitas Mandiri (Portability & Self-Contained): Aplikasi dikemas dalam berkas biner Windows (.exe) yang membundel runtime PHP 8.3 portabel dan dependensi Visual C++ Runtime (CRT), sehingga dapat dijalankan langsung tanpa instalasi server web lokal (Laragon/XAMPP), Composer, maupun Node.js.
4. Aspek Keandalan Data (Reliability): Seluruh transaksi data memenuhi standar ACID pada cloud database PostgreSQL, sementara berkas fisik dokumen tersimpan pada cloud storage privat yang aman dari risiko kerusakan perangkat keras lokal.
5. Aspek Antarmuka Pengguna (Usability): Desain antarmuka menerapkan prinsip ergonomi visual modern yang responsif, kontras warna yang nyaman, serta penataan tombol aksi yang intuitif guna meminimalkan kurva pembelajaran pengguna.

Perancangan basis data bertujuan untuk menyusun struktur penyimpanan data yang efisien, bebas dari anomali redundansi, serta mematuhi kaidah normalisasi dan integritas referensial (Silberschatz et al., 2020; Connolly & Begg, 2015). Basis data SIAPTIKA diimplementasikan menggunakan PostgreSQL pada cloud Supabase.

a. Entity Relationship Diagram (ERD)
Entity Relationship Diagram (ERD) menggambarkan hubungan logis antarentitas data di dalam sistem SIAPTIKA. Struktur basis data terdiri atas 3 (tiga) entitas utama:
1. Entitas `users`: Menyimpan data akun administratif instansi.

3.2.6 Perancangan Arsitektur Perangkat Lunak (Software Architecture)

Perancangan arsitektur perangkat lunak mendefinisikan struktur fundamental sistem, komponen komputasi, serta pola interaksi antarlapisan (multi-tier architecture) guna memenuhi kriteria fungsional dan atribut kualitas sistem (Bass et al., 2021; Griffiths, 2019). Sistem SIAPTIKA dirancang dengan pola 4-Tier Hybrid Desktop Architecture:

1. Presentation Tier (Lapisan Antarmuka): Diimplementasikan menggunakan jendela desktop Electron berbasis Chromium engine yang merender antarmuka pengguna interaktif melalui Blade template engine dan styling CSS kustom. Lapisan ini menangani penangkapan aksi pengguna, validasi sisi klien, serta visualisasi data tabel dan modal.
2. Application / Logic Tier (Lapisan Logika Bisnis): Dijalankan oleh server internal Laravel di latar belakang pada alamat loopback lokal 127.0.0.1. Lapisan ini memuat controller (ActivityController, DocumentController, AuthController), middleware otorisasi sesi, serta business service layer (DocumentService) yang mengatur aturan bisnis pengunggahan dan penghapusan arsip.
3. Data Access Tier (Lapisan Akses Data): Dikelola oleh Eloquent ORM yang bertugas mengabstraksi operasi CRUD dan pemetaan relasi model secara berorientasi objek terhadap skema basis data relasional.
4. Cloud Infrastructure Tier (Lapisan Infrastruktur Cloud): Berada pada platform cloud Supabase yang memuat PostgreSQL database engine (menyimpan rekaman tabular data terenkripsi) dan Supabase Storage S3 (menyimpan berkas fisik arsip kedinasan di dalam private bucket).

3.3.2 Implementasi Basis Data dan Integrasi Cloud Supabase

Implementasi basis data memanfaatkan Database Migration bawaan Laravel guna memastikan pembuatan skema tabel relasional berjalan secara terstruktur, terversi, dan konsisten antar-lingkungan pengembangan (Stauffer, 2019). Tiga migrasi utama yang dieksekusi meliputi:
1. Tabel users: Dikonfigurasi dengan kolom login_id unik bertipe VARCHAR(255) sebagai pengganti email standar guna mendukung ID kepegawaian resmi (ADM001), serta kolom password untuk menampung string hasil enkripsi satu arah.
2. Tabel activities: Membangun struktur penyimpanan agenda kedinasan dengan foreign key user_id yang berelasi ke tabel users, title, activity_date (diberi indeks kueri), time, location, description (nullable), serta status bertipe ENUM ('scheduled', 'completed') dengan nilai baku 'scheduled'.
3. Tabel documents: Membangun relasi kearsipan dengan foreign key activity_id, kategori document_type bertipe ENUM ('surat', 'notulen', 'dokumentasi'), nama asli berkas (file_name), dan lokasi objek berkas pada cloud storage (file_url).

Koneksi jaringan dikonfigurasi melalui berkas .env dengan menghubungkan PDO PostgreSQL Laravel ke Supabase Transaction Pooler (port 6543) dan Session Pooler (port 5432) berenkripsi SSL/TLS (sslmode=require). Penyimpanan fisik dokumen diarahkan ke private bucket 'documents' pada Supabase Storage menggunakan protokol API berbasis AWS S3 SDK yang dilindungi token otorisasi aman.


3.3.3 Implementasi Modul Autentikasi dan Otorisasi Administrator

Modul autentikasi dan otorisasi bertugas menjaga keamanan hak akses dan integritas data administratif sistem melalui kelas AuthController pada ruang nama App\Http\Controllers\Auth (Laudon & Laudon, 2020):
1. Verifikasi Kredensial: Sistem mencocokkan input login_id dan memverifikasi kata sandi menggunakan fungsi Hash::check() berbasis algoritma hash Bcrypt dengan salt dinamis yang tahan terhadap ancaman kamus dan rainbow table (Stauffer, 2019).
2. Proteksi Sesi & Rute: Saat otentikasi sukses, sesi login Administrator diaktifkan dan fungsi $request->session()->regenerate() secara wajib dieksekusi guna mencegah serangan Session Fixation. Seluruh rute administratif (/admin/*) diproteksi oleh middleware autentikasi kustom yang mencegat akses tanpa izin dan mengarahkannya kembali ke halaman login.
3. Penutupan Sesi (Logout): Tombol keluar memicu $request->session()->invalidate() untuk memusnahkan data sesi dari memori dan $request->session()->regenerateToken() untuk memperbarui token proteksi Cross-Site Request Forgery (CSRF).


3.3.4 Implementasi Modul Manajemen Kegiatan Kedinasan (CRUD)

Modul manajemen kegiatan kedinasan dikendalikan oleh ActivityController pada ruang nama App\Http\Controllers\Admin yang memanfaatkan model Eloquent Activity (Stauffer, 2019):
1. Penambahan Agenda (Create): Menerima masukan formulir modal, memvalidasi kelengkapan data, dan mengeksekusi Activity::create() untuk menyimpan agenda baru ke database PostgreSQL di Supabase dengan status awal 'scheduled'.
2. Penyajian & Penyaringan Data (Read): Mengambil kumpulan data agenda dari cloud database menggunakan kueri dinamis Eloquent berbasis kata kunci judul/lokasi, penyaringan status kegiatan (Semua, Terjadwal, Selesai), dan pengurutan kronologis yang disajikan melalui teknik paginasi data (pagination).
3. Pembaruan & Penghapusan (Update & Delete): Mendukung pengubahan rincian agenda dan status kegiatan menjadi 'completed', serta penghapusan rekaman kegiatan dengan verifikasi relasi arsip terkait terlebih dahulu demi integritas referensial data.


3.3.5 Implementasi Modul Pengarsipan Dokumen Terpusat (Upload & Streaming Proxy)

Pengelolaan berkas arsip kedinasan (Surat Perintah Tugas, Notulen Rapat, dan Dokumentasi Foto) diimplementasikan melalui kelas DocumentService pada ruang nama App\Services menerapkan Service Layer Pattern (Fowler, 2018):
1. Transaksi Penyimpanan Atomik (ACID): Fisik berkas biner terlebih dahulu diunggah ke bucket privat Supabase Storage via protokol S3 (documents/{activity_id}/{unique_file_name}), kemudian pencatatan metadata dibungkus di dalam blok transaksi atomik DB::transaction(). Apabila terjadi galat basis data, transaksi dibatalkan (rollback) dan berkas pada cloud storage otomatis dihapus kompensasi ($this->storage->delete($path)) guna mencegah timbulnya berkas sampah yatim (Silberschatz et al., 2020).
2. Penggantian Berkas Terkendali: Berkas pengganti diverifikasi dan diunggah sebelum berkas fisik lama dihapus, memastikan dokumen dinas tidak hilang jika proses unggah terputus di tengah jalan.
3. Pengaliran Berkas Melalui Perantara (Streaming Proxy): Seluruh arsip disimpan di bucket cloud privat. Untuk menampilkan pratinjau naskah dokumen (inline viewer) format PDF dan gambar, DocumentController mengunduh aliran data berkas secara privat di sisi server lokal dan mengalirkannya langsung ke antarmuka dengan header HTTP Content-Type yang sesuai, sehingga berkas dapat dibaca langsung tanpa mengekspos tautan URL privat ke publik.


3.3.6 Implementasi Dashboard Informasi Pegawai (Portal Read-Only)

Dashboard pegawai dikendalikan oleh DashboardController dan ActivityController pada modul Employee guna menyajikan transparansi agenda kedinasan tanpa keharusan mengingat akun atau melakukan login (Zero-Authentication Access) (Laudon & Laudon, 2020):
1. Agregasi Statistik Real-Time: Sistem mengeksekusi kueri agregasi otomatis untuk menghitung total kegiatan, kegiatan hari ini, agenda mendatang, dan total berkas arsip saat aplikasi dibuka.
2. Penyajian Informasi Terbuka: Menyajikan panel kartu metrik statistik, widget jam waktu nyata, jadwal agenda hari ini, serta bilah pencarian teks instan dan direktori penelusuran arsip.
3. Pengamanan Hak Akses Baca-Saja: Modul pegawai secara ketat hanya menyediakan rute HTTP berjenis GET dan meniadakan seluruh tombol aksi manipulasi data (Tambah, Edit, Hapus, Unggah) pada kode templat Blade, menjamin bahwa sistem beroperasi dalam mode peninjauan murni tanpa risiko modifikasi data yang tidak sengaja.


3.3.7 Implementasi Pengemasan Aplikasi Desktop Mandiri (Electron Packaging & Bundling)

Implementasi pengemasan desktop menggabungkan seluruh komponen sistem ke dalam paket biner mandiri (.exe) berbasis Windows tanpa dependensi perangkat lunak eksternal (Griffiths, 2019; Bass et al., 2021):
1. Skrip Pengendali Siklus Hidup (laravel-bridge.js): Mengaktifkan web server lokal internal melalui child_process.spawn('php', ['artisan', 'serve']), mengimplementasikan fallback pemindaian port otomatis jika port 8000 sedang terpakai, memantau kesiapan server melalui polling berkala pada rute /up hingga status HTTP 200 OK, serta mengeksekusi penghentian bersih (graceful shutdown) sub-proses PHP saat jendela aplikasi ditutup.
2. Pembundelan Runtime Portabel: Paket aplikasi membundel folder runtime/php yang memuat biner PHP 8.3 Thread-Safe, berkas php.ini mandiri dengan ekstensi esensial (pdo_pgsql, openssl, curl, fileinfo), berkas pustaka dependensi Visual C++ Runtime (msvcp140.dll, vcruntime140.dll), serta sertifikat keamanan Mozilla (cacert.pem) untuk menjamin jabat tangan enkripsi SSL/TLS dengan cloud Supabase.
3. Konfigurasi Pembuatan Installer (electron-builder): Mengompilasi dua paket penginstal Windows berbasis NSIS, yaitu SIAPTIKA Administrator Setup.exe untuk administrator pengelola data dan SIAPTIKA Dashboard Setup.exe untuk pegawai umum, yang dapat langsung dioperasikan secara plug-and-play tanpa instalasi server web lokal eksternal.

Melalui tahapan ini, kestabilan, keandalan, dan ketahanan sistem diuji secara empiris guna memastikan bahwa SIAPTIKA siap dioperasikan dalam lingkungan kerja kedinasan sehari-hari.

Hasil implementasi antarmuka SIAPTIKA merupakan realisasi konkret dari SIAPTIKA Design System berbasis Serif Style yang telah dimodelkan pada Subbab 3.2.7. Antarmuka terdistribusi ke dalam dua aplikasi desktop mandiri siap pakai berbasis installer Windows (.exe):

a. Antarmuka SIAPTIKA Administrator

1. Autentikasi dan Dasbor Utama: Menyajikan form login terpusat berbasis ID ADM001 dan kata sandi, serta dasbor utama yang memuat empat kartu metrik statistik (Total Kegiatan, Hari Ini, Mendatang, dan Total Arsip), widget penunjuk jam waktu nyata, dan ringkasan agenda terdekat.
2. Pengelolaan Agenda dan Formulir Modal: Tabel agenda kedinasan dilengkapi pencarian instan, filter status kegiatan, dan tombol aksi kontekstual (Detail, Edit, Hapus). Penambahan dan penyuntingan agenda dilakukan melalui jendela modal terfokus (backdrop blur) dengan validasi interaktif.
3. Manajemen Kearsipan dan Pratinjau Dokumen: Panel kearsipan terpadu membagi berkas ke dalam tiga kategori dinas (Surat Tugas, Notulen, Foto Kegiatan) dengan fitur unggah seret-dan-lepas serta penampil dokumen mandiri (inline viewer) format PDF dan gambar via streaming proxy.

b. Antarmuka SIAPTIKA Dashboard Pegawai
Menghadirkan portal keterbukaan informasi dinas yang transparan, mudah diakses, dan aman:
1. Dasbor Informasi Terbuka (Read-Only): Menyajikan tata letak visual yang identik dengan dasbor admin (kartu metrik, jam sistem, agenda hari ini dan mendatang) yang dapat diakses langsung tanpa prosedur login (Zero-Authentication Access).
2. Penelusuran Cepat dan Direktori Arsip: Pegawai dapat menelusuri agenda berdasarkan kata kunci judul/lokasi dan membuka pratinjau dokumen arsip naskah dinas untuk mendukung koordinasi kerja lintas seksi.
3. Isolasi Keamanan Visual: Seluruh elemen manipulasi data (tombol Tambah, Edit, Hapus, Unggah) ditiadakan secara mutlak pada antarmuka pegawai, menjamin sistem beroperasi murni dalam mode peninjauan tanpa risiko perubahan data tidak sengaja.

c. Penanganan Galat dan Ketahanan Visual Sistem
Sistem mengimplementasikan halaman penanganan galat kustom bertema kedinasan (Error 404 dan Error 403) berbahasa Indonesia santun dan informatif, dilengkapi tombol navigasi kembali ke beranda sistem yang menyesuaikan peran pengguna secara kontekstual.


3.4.2 Hasil Pengujian Fungsional (Black Box Testing)

Pengujian perangkat lunak dilakukan menggunakan metode Black Box Testing (Pengujian Kotak Hitam). Pendekatan ini berfokus pada pengujian fungsionalitas eksternal perangkat lunak berdasarkan masukan (input) yang diberikan dan keluaran (output) yang dihasilkan tanpa harus memeriksa struktur internal kode program secara langsung (Pressman & Maxim, 2020).

a. Lingkungan dan Skenario Pengujian
Pengujian fungsional dilaksanakan pada lingkungan operasional kerja riil di kantor Bidang APTIKA Diskominfotik Provinsi Riau dengan spesifikasi lingkungan pengujian sebagai berikut:
1. Perangkat Keras Pengujian: Komputer Desktop PC Intel Core i5 @ 3.00 GHz, RAM 16 GB, SSD 512 GB, Monitor Layar FHD 1080p, serta Laptop Windows 11 portabel untuk pengujian multi-perangkat.
2. Lingkungan Perangkat Lunak: Sistem Operasi Windows 11 64-bit, paket aplikasi biner SIAPTIKA Administrator Setup.exe dan SIAPTIKA Dashboard Setup.exe hasil kompilasi akhir.
3. Lingkungan Jaringan: Koneksi jaringan intranet dan internet kantor Diskominfotik Riau dengan latensi rata-rata 25-40 ms menuju server cloud Supabase.

Skenario pengujian disusun secara komprehensif mencakup 37 (tiga puluh tujuh) kasus uji yang mewakili seluruh aspek fungsional sistem, meliputi:
- Modul 1: Autentikasi Administrator (5 skenario)
- Modul 2: Kontrol Akses dan Keamanan Rute (4 skenario)
- Modul 3: Manajemen Kegiatan Kedinasan / CRUD (8 skenario)
- Modul 4: Pengarsipan dan Manajemen Dokumen (8 skenario)
- Modul 5: Dashboard Informasi dan Penelusuran Pegawai (6 skenario)
- Modul 6: Siklus Hidup Aplikasi Desktop dan Penanganan Galat (6 skenario)

3.4.3 Analisis dan Pembahasan

Berdasarkan hasil implementasi dan pengujian fungsional yang telah dilaksanakan, dilakukan analisis dan pembahasan mendalam terhadap efektivitas penerapan sistem informasi SIAPTIKA di lingkungan Bidang APTIKA Diskominfotik Provinsi Riau:

a. Analisis Efektivitas Penggunaan ID Administrator (ADM001)
Penggunaan ID Administrator terpusat (ADM001) terbukti memberikan efektivitas operasional yang jauh lebih tinggi dibandingkan model registrasi akun berbasis alamat email pribadi (Laudon & Laudon, 2020). Dalam tata kelola instansi pemerintah, tanggung jawab pengelolaan arsip kegiatan kedinasan melekat secara institusional pada fungsi jabatan operasional, bukan kepemilikan personal pegawai. Penerapan ID terpusat ini memberikan keuntungan strategis:
1. Peniadaan Ketergantungan Akun Pribadi: Menghilangkan risiko kelumpuhan pengelolaan arsip apabila personel operator mengalami mutasi kerja, rotasi bagian, atau cuti dinas, karena akses kepengurusan sistem dapat didelegasikan secara mulus kepada pelaksana tugas tanpa prosedur pemindahan kepemilikan akun email.
2. Pencegahan Fragmentasi Data: Seluruh kegiatan dan dokumen yang dihimpun tercatat di bawah satu entitas kepengurusan resmi yang seragam, sehingga tidak terjadi kebingungan mengenai kepemilikan berkas dinas.
3. Perlindungan Kredensial Maksimal: Verifikasi kata sandi berbasis algoritma satu arah Bcrypt dengan salt dinamis menjamin bahwa kredensial tunggal ini terlindungi secara kriptografis dari ancaman pencurian hash atau pembobolan data (Stauffer, 2019).

b. Analisis Keunggulan Arsitektur Hybrid Desktop Tanpa Server Publik
Penerapan arsitektur Hybrid Desktop (memadukan aplikasi desktop Electron, runtime server PHP lokal mandiri, dan basis data cloud Supabase) membuktikan keunggulan arsitektural yang sangat signifikan bagi instansi pemerintah tingkat daerah (Griffiths, 2019; Bass et al., 2021):
1. Efisiensi Anggaran Operasional: Instansi terbebas secara permanen dari biaya sewa server publik bulanan (VPS/Cloud Hosting) yang biasanya membebani anggaran dinas, karena beban komputasi pemrosesan logika backend ditanggung sepenuhnya oleh komputer lokal pengguna (client-side execution).
2. Ketahanan dan Keamanan Jaringan: Aplikasi tidak mengekspos port layanan web apa pun ke internet publik. Seluruh komunikasi data keluar hanya berupa koneksi kueri terenkripsi SSL/TLS (port 5432/6543) ke Supabase Database dan protokol API S3 ke Supabase Storage, sehingga secara drastis meminimalisir bidang sasaran serangan siber (attack surface) seperti serangan DDoS, injeksi skrip publik, atau pemindaian port peretas.
3. Kemudahan Distribusi Mandiri (Zero-Dependency Setup): Melalui pembundelan portable runtime PHP 8.3 dan pustaka pendukung di dalam installer .exe, staf dinas tidak perlu memahami instalasi web server pihak ketiga (seperti XAMPP, Laragon, atau konfigurasi path environment Windows). Aplikasi dapat langsung diinstal dan berjalan seketika (plug-and-play).

c. Analisis Efisiensi Pengelolaan Arsip Digital Terintegrasi
Sebelum implementasi SIAPTIKA, tata kelola administrasi kegiatan dan kearsipan pada Bidang APTIKA berjalan secara konvensional dan terpecah di berbagai media fisik (ordner lemari arsip) serta ruang penyimpanan personal komputer staf (Sutirman, 2019; Ferreira et al., 2018). Kondisi tersebut mengakibatkan waktu penelusuran dokumen surat tugas dan notulen rapat membutuhkan waktu relatif lama, bahkan kerap kali berkas fisik terselip atau rusak.

Setelah penerapan sistem SIAPTIKA:
1. Akselerasi Waktu Temu Kembali Informasi: Melalui fitur pencarian terpadu dan direktori arsip digital berbasis cloud, waktu pencarian dan penemuan kembali naskah dokumen kedinasan terpangkas drastis menjadi jauh lebih cepat.
2. Integrasi Siklus Hidup Kegiatan dan Kearsipan: Dokumen arsip tidak lagi terpisah dari konteks kegiatannya; surat perintah tugas, notulen rapat, dan dokumentasi visual terikat secara relasional pada satu entitas agenda kerja dinas yang utuh.
3. Transparansi Tanpa Mengorbankan Keamanan: Pemisahan aplikasi menjadi portal baca-saja bagi pegawai dan portal autentikasi penuh bagi administrator berhasil mewujudkan asas keterbukaan informasi di lingkungan kantor dinas, sekaligus menjaga integritas naskah dinas dari risiko modifikasi atau penghapusan data yang tidak disengaja.


BAB IV KESIMPULAN DAN SARAN


4.1 Kesimpulan

Pengembangan Sistem Informasi Administrasi Penyelenggaraan TIK dan Aplikasi (SIAPTIKA) berhasil diselesaikan sebagai solusi digital terintegrasi guna mengatasi kendala keterceceran arsip dokumen kedinasan dan lambatnya koordinasi agenda kerja pada Bidang Aplikasi Informatika (APTIKA) Diskominfotik Provinsi Riau. Melalui implementasi arsitektur Hybrid Desktop yang memadukan framework Laravel 11, runtime desktop Electron mandiri, serta infrastruktur cloud Supabase, sistem ini berhasil diwujudkan ke dalam dua aplikasi desktop mandiri siap pakai (self-contained)—yaitu SIAPTIKA Administrator untuk pengelolaan data kedinasan terautentikasi dan SIAPTIKA Dashboard untuk portal pemantauan agenda pegawai secara terbuka (read-only)—yang dapat dioperasikan secara langsung tanpa memerlukan instalasi server web tambahan maupun beban biaya sewa hosting publik.

Berdasarkan evaluasi pengujian fungsional menggunakan metode Black Box Testing terhadap 37 (tiga puluh tujuh) skenario uji kasus, seluruh modul perangkat lunak terbukti beroperasi dengan tingkat keandalan 100% Lolos (PASS) tanpa ditemukan adanya galat kritis maupun celah otorisasi rute. Penerapan standardisasi identitas institusional ADM001, penegakan integritas transaksi database atomik (ACID) dengan mekanisme rollback otomatis pada modul kearsipan, serta pengaliran berkas privat melalui streaming proxy terbukti efektif mengamankan naskah resmi dinas (surat tugas, notulen rapat, dan dokumentasi foto), sekaligus mempercepat waktu temu kembali informasi bagi seluruh aparatur di lingkungan kantor.


4.2 Saran

Demi keberlanjutan dan penyempurnaan sistem SIAPTIKA pada masa yang akan datang, diajukan beberapa saran pengembangan strategis:
1. Pengembangan Modul Ekspor Laporan Otomatis: Penambahan fitur rekapitulasi agenda dan berkas arsip secara otomatis ke dalam format PDF atau spreadsheet Excel berdasarkan rentang periode anggaran (triwulanan atau tahunan) guna mempermudah penyusunan laporan pertanggungjawaban kinerja instansi.
2. Notifikasi Pengingat Desktop Terjadwal: Integrasi pemberitahuan otomatis (desktop push notification) pada sistem operasi Windows guna mengingatkan pengguna mengenai agenda kedinasan beberapa jam sebelum pelaksanaan acara.
3. Mekanisme Pencadangan Data Mandiri: Penyediaan fitur pencadangan basis data lokal (local database backup) secara berkala sebagai langkah mitigasi redundan terhadap potensi kendala koneksi jaringan internet di lingkungan kantor.

4.2 Landasan Teori Transisi dan Alih Kelola Perangkat Lunak (Software Handover)
Proses serah terima perangkat lunak (software handover) dari pihak pengembang kepada pihak pemangku kepentingan organisasi merupakan tahapan krusial dalam siklus hidup rekayasa perangkat lunak (ISO/IEC/IEEE, 2017). Berdasarkan standar internasional ISO/IEC/IEEE 12207:2017 pada klausul 6.4.10 mengenai Transition Process, transisi sistem bertujuan untuk mentransfer tanggung jawab operasional dari lingkungan pengembangan ke lingkungan pengguna nyata secara terencana, termasuk penyerahan konfigurasi teknis, basis data, hak akses administratif, serta dokumentasi pemeliharaan agar sistem dapat beroperasi mandiri secara berkelanjutan tanpa gangguan layanan.

Dalam perspektif pemeliharaan perangkat lunak jangka panjang, penelitian empiris oleh Ikram et al. (2018) menegaskan bahwa kegagalan alih kelola perangkat lunak pada organisasi sering kali dipicu oleh ketimpangan transfer pengetahuan (knowledge transfer gap) dan hilangnya artefak kredensial ketika pengembang awal meninggalkan proyek. Untuk memitigasi risiko single point of knowledge failure tersebut, transfer kepemilikan harus mencakup penyerahan repositori kode sumber yang terstruktur rapi, dokumentasi skema data, pemusatan akun otorisasi, serta ketersediaan media distribusi aplikasi yang siap pakai (Pressman & Maxim, 2020; Sommerville, 2016). Melalui penyediaan akun induk tunggal dan kanal distribusi ganda (GitHub Releases dan Google Drive), instansi menerima kejelasan tata kelola teknis yang transparan dan dapat dikelola oleh staf aparatur tanpa ketergantungan personal terhadap mahasiswa pelaksana Kerja Praktik.

5.1 DokumenService.php (Orkestrasi Transaksi Atomik ACID dan Pengunggahan Storage S3)
Lokasi Berkas: app/Services/DocumentService.php

```php
<?php

namespace App\Services;

use App\Models\Activity;
use App\Models\Document;
use Illuminate\Http\UploadedFile;
use Illuminate\Support\Facades\DB;

class DocumentService
{
    public function __construct(
        private readonly StorageServiceInterface $storage,
    ) {}

    public function upload(
        UploadedFile $file,
        Activity $activity,
        string $documentType,
    ): Document {
        // Langkah 1: Unggah berkas fisik ke Supabase Cloud Storage S3
        $path = $this->storage->upload(
            file:      $file,
            directory: "documents/{$activity->id}",
        );

        try {
            // Langkah 2: Simpan metadata ke database dalam transaksi atomik
            $document = DB::transaction(function () use ($file, $activity, $documentType, $path): Document {
                return Document::create([
                    'activity_id'   => $activity->id,
                    'document_type' => $documentType,
                    'file_name'     => $file->getClientOriginalName(),
                    'file_url'      => $this->storage->url($path),
                    'file_path'     => $path,
                    'file_size'     => $file->getSize(),
                    'mime_type'     => $file->getMimeType(),
                ]);
            });

            return $document;
        } catch (\Throwable $e) {
            // Langkah 3: Rollback berkas fisik dari Storage jika insert metadata DB gagal
            $this->storage->delete($path);
            throw $e;
        }
    }
}
```

5.2 Activity.php (Model Eloquent dengan Mutator Casting dan Relasi Antar-Tabel)
Lokasi Berkas: app/Models/Activity.php

```php
<?php

namespace App\Models;

use Carbon\Carbon;
use Illuminate\Database\Eloquent\Factories\HasFactory;
use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\Relations\BelongsTo;
use Illuminate\Database\Eloquent\Relations\HasMany;

class Activity extends Model
{
    use HasFactory;

    protected $table = 'activities';

    protected $fillable = [
        'user_id',
        'title',
        'activity_date',
        'time',
        'location',
        'description',
        'status',
    ];

    protected function casts(): array
    {
        return [
            'activity_date' => 'date',
            'time'          => 'string',
        ];
    }

    public function user(): BelongsTo
    {
        return $this->belongsTo(User::class, 'user_id');
    }

    public function documents(): HasMany
    {
        return $this->hasMany(Document::class, 'activity_id');
    }

    public function getComputedStatusAttribute(): string
    {
        $today = Carbon::today();
        $actDate = Carbon::parse($this->activity_date)->startOfDay();

        if ($actDate->gt($today)) {
            return 'Direncana';
        } elseif ($actDate->eq($today)) {
            return 'Sudah Berlangsung';
        } else {
            return 'Selesai';
        }
    }
}
```

5.3 laravel-bridge.js (Manajemen Child Process PHP Lokal dan Polling Kesiapan HTTP Server)
Lokasi Berkas: electron/shared/laravel-bridge.js

```javascript
'use strict';

const { spawn } = require('child_process');
const http       = require('http');
const path       = require('path');
const fs         = require('fs');

const LARAVEL_HOST      = '127.0.0.1';
const LARAVEL_PORT_BASE = 8000;
const HEALTH_ENDPOINT   = '/up';
const POLL_INTERVAL     = 350;
const POLL_TIMEOUT      = 60000;

let laravelProcess = null;

function startLaravelServer(basePath) {
    return new Promise((resolve, reject) => {
        const phpBinary = path.join(basePath, 'runtime', 'php', 'php.exe');
        const artisanPath = path.join(basePath, 'artisan');

        laravelProcess = spawn(phpBinary, [artisanPath, 'serve', `--host=${LARAVEL_HOST}`, `--port=${LARAVEL_PORT_BASE}`], {
            detached: false,
            stdio: 'ignore'
        });

        const startTime = Date.now();
        const checkServer = () => {
            http.get(`http://${LARAVEL_HOST}:${LARAVEL_PORT_BASE}${HEALTH_ENDPOINT}`, (res) => {
                if (res.statusCode === 200) {
                    resolve(`http://${LARAVEL_HOST}:${LARAVEL_PORT_BASE}`);
                } else {
                    retry();
                }
            }).on('error', retry);
        };

        const retry = () => {
            if (Date.now() - startTime > POLL_TIMEOUT) {
                reject(new Error('Server startup timed out'));
            } else {
                setTimeout(checkServer, POLL_INTERVAL);
            }
        };

        checkServer();
    });
}

function stopLaravelServer() {
    if (laravelProcess) {
        laravelProcess.kill('SIGTERM');
        laravelProcess = null;
    }
}

module.exports = { startLaravelServer, stopLaravelServer };
```
